Task 1 (Introduction): Hook: purple team exercise PT-2026-09 showed that the red team downloaded tools onto two exercise hosts with the built-in Windows certificate utility (certutil.exe), once under its own name and once as a renamed copy, and no detection fired. Finding F-03 became requirement REQ-0412, and you are the engineer who must turn it into a production detection, DET-0217. Why it matters: a rule written straight into production without a spec, tests or staged deployment either misses variants or floods analysts. Scope: the lifecycle of one detection (requirement, spec, build, test, deploy, tune) with a spec workbench practical. Out of scope, with pointers: Sigma syntax (Writing Effective Sigma Rules), generating telemetry with Atomic tests (Atomic Red Team for Detection Validation), correlation rules and outcome definitions (SIEM Engineering & Detection Rule Writing). Question: Type "yes".
Task 2 (The Detection Lifecycle and the Requirement): Teach the six stages in order as an SVG loop with labelled outputs: Requirement (a written need: behaviour, scope, why), Spec (the detection spec document), Build (the rule logic), Test (test cases run with results recorded), Deploy (shadow mode first, then production), Tune (changes from shadow or production results, which loop back to Test). One sentence: a detection that no longer serves a requirement is retired (governance is covered in Use Case Development Lifecycle). Requirement sources table: threat intelligence report, incident lessons learned, purple team finding, hunt result. Behaviour versus indicator table: "certutil downloading a file from a web address" (behaviour, survives new infrastructure) versus "IP address 203.0.113.58" or "file hash of sv.bin" (indicator, changes with each campaign). Map the behaviour to one ATT&CK technique: T1105 Ingress Tool Transfer (certutil is a listed procedure), and show two near techniques that also use certutil so learners do not mix them up: T1140 Deobfuscate/Decode Files or Information (certutil -decode) and T1553.004 Install Root Certificate (certutil -addstore). Questions (3): Which stage of the lifecycle comes immediately after Deploy? (one word, the stage name as shown in the lifecycle diagram) (answer: Tune); What type of value, such as a single file hash or IP address, should a requirement avoid relying on by itself? (one word) (answer: indicator); Which ATT&CK technique ID covers transferring tools or files from an external system into an environment? (format T followed by four digits) (answer: T1105).
Task 3 (Writing the Detection Spec): Teach the spec as the contract every later stage works from, based on the Alerting and Detection Strategy (ADS) idea. Spec field table: Detection ID, Title, Version, Status (draft, shadow, production, retired), Owner, Behaviour and ATT&CK technique, Data source and required fields, Logic summary in plain language, Known benign activity, Test cases (ID, event, expected result Alert or No alert), Success criteria, Response notes, Changelog. Data source section: compare Sysmon Event ID 1 (Process creation) with Security event 4688 in a table: 4688 records NewProcessName, ParentProcessName (Windows 10 and Server 2016 and later) and CommandLine only when the policy "Include command line in process creation events" is enabled, and it has no original file name; Sysmon Event ID 1 records Image, OriginalFileName, CommandLine, ParentImage, User, IntegrityLevel and more. Explain OriginalFileName: it comes from the PE version information inside the binary, so it still reads CertUtil.exe after the file is copied to another name, while Image shows the new path. Success criteria for DET-0217 (as an ordered list): every test case marked Alert fires; no test case marked No alert fires; every shadow mode alert is reviewed and no unexplained false positive remains; the full test suite passes again after every change. Questions (3): Which Sysmon event ID records process creation? (answer in digits) (answer: 1); Which Sysmon process creation field still identifies a binary after it has been renamed on disk? (field name exactly as Sysmon writes it) (answer: OriginalFileName); Which spec field states the measurable conditions a detection must meet before it can be promoted? (two words) (answer: success criteria).
Task 4 (Building and Testing Against Test Cases): Teach test first: test cases and their expected results are written in the spec before any logic is built, so the tests describe the requirement and not the rule. Test case types table: true positive samples (one per known variant: plain name, renamed copy, slash switch syntax such as /urlcache, a process running as SYSTEM from a scheduled task), near miss test cases (benign events that share the binary, a switch or a keyword with the behaviour, for example certutil -urlcache * delete clearing the URL cache, certutil -verify -urlfetch checking a certificate chain, or findstr searching a log export for the word urlcache), and out-of-scope cases (another download tool such as curl.exe, covered by a different requirement). A test passes when the actual result equals the expected result. Rule logic concepts: a condition is field, operator, value; operators equals, contains, starts with, ends with; all conditions must match; matching is case-insensitive. Robustness tips with the certutil example: prefer OriginalFileName to Image for a binary that can be renamed; match the switch word (urlcache) rather than one prefix (-urlcache) because certutil accepts both - and / prefixes; never change or delete a test case just to make the suite pass. Regression testing: re-run the whole suite after every rule change, including tuning. Say plainly that turning this logic into Sigma is the next room and generating new true positive samples with Atomic tests is the room after; do not show Sigma YAML or Atomic test syntax. Questions (3): What is a benign test case called when it shares the binary, a switch or a keyword with the target behaviour? (two words) (answer: near miss); Which operator should a condition use when the value can appear anywhere inside the command line? (one word) (answer: contains); What is re-running the whole test suite after every rule change called? (two words) (answer: regression testing).
Task 5 (Deploy, Tune and Version): Teach deployment in two steps: shadow mode (the rule runs on live telemetry and records its matches for the engineer to review, but sends nothing to the analyst queue) for a fixed window, here 7 days, then production alerting. Reviewing shadow results: classify each match using the outcome terms from SIEM Engineering & Detection Rule Writing (not redefined here). Tuning: add the narrowest exclusion that removes the explained false positives, using at least two fields together (for example parent process and URL host); never exclude a whole account class such as NT AUTHORITY\SYSTEM or a whole host, because true positives can run there too (for example, a scheduled task runs as SYSTEM). After tuning, re-run the full suite. Versioning: MAJOR.MINOR.PATCH adapted for detections in a table: MAJOR when the behaviour or data source changes; MINOR when the logic changes but the behaviour stays the same (a new condition or a new exclusion); PATCH when only metadata changes (description, references, typos) and the logic does not. Drafts use 0.x; the first deployed version is 1.0.0; promotion changes the Status field, not the version. Changelog entry fields: date, version, author, change, reason, test result. Teach the graded order as an ordered list and an SVG flow: 1) record the requirement; 2) write the spec with test cases and expected results; 3) build the logic; 4) run the test suite until every case passes; 5) deploy version 1.0.0 in shadow mode; 6) add the narrow exclusion and raise the version with a changelog entry (these two in either order); 7) re-run the full test suite on the new version; 8) promote to production with owner and response notes. List the anti-patterns as a "never do" box: deploying straight to production, deleting a failing test case, excluding all SYSTEM activity, editing a live rule without a new version, writing logic first and picking tests it already passes. Questions (3): Which deployment mode runs a rule on live telemetry and records its matches without sending alerts to analysts? (two words) (answer: shadow mode); In this room's versioning scheme, which part of the version number rises when only the description or references change? (one word) (answer: patch); Which record lists every change to a detection with its date, version and reason? (one word) (answer: changelog).
Task 6 (Practical): Launch the Detection Spec Workbench. Questions (2): Which parent process launched every false positive that version 1.0.0 raised during the shadow week? (file name with extension) (answer: pkgrelay.exe); Enter the flag shown after the proof and the lifecycle record are accepted. (answer: CBX{promote_detection})
Task 7 (Conclusion): Recap the six stages and what each produces, the spec fields, test first with true positive and near miss cases, regression after every change, shadow mode before production, narrow exclusions, MAJOR.MINOR.PATCH and the changelog. Reusable artefact: a one-page detection spec template (the field table from Task 3 with empty rows) and a promotion checklist (suite passes, shadow alerts reviewed, exclusions use two or more fields, version raised and changelog written, owner and response notes set). - Technical accuracy notes (verified):
  - Sysmon Event ID 1 (Process creation) records UtcTime, ProcessGuid, ProcessId, Image, FileVersion, Description, Product, Company, OriginalFileName, CommandLine, CurrentDirectory, User, LogonGuid, LogonId, TerminalSessionId, IntegrityLevel, Hashes, ParentProcessGuid, ParentProcessId, ParentImage, ParentCommandLine (and ParentUser in current versions); Computer comes from the event's System section. OriginalFileName is read from the PE version resource, so a copied and renamed certutil still reports CertUtil.exe. Sources: EventSentry Sysmon Event ID 1 reference (https://system32.eventsentry.com/sysmon/event/1), Gravwell "What's in a Sysmon Event Pt. 1" (https://gravwell.io/blog/sysmon-event-pt.-1-process-creation); SigmaHQ rule "Suspicious Download Via Certutil.EXE" (proc_creation_win_certutil_download) matches Image ending in \certutil.exe OR OriginalFileName CertUtil.exe, plus urlcache and http in CommandLine (https://detection.fyi/sigmahq/sigma/windows/process_creation/proc_creation_win_certutil_download/).
  - Sysmon v15.15 released 23 July 2024, schema 4.90 (https://www.deskmodder.de/blog/?p=190942, Adaptiva patch listing https://adaptiva.com/patch-library/1000001714_patch_for_sysmon_x86). Microsoft has announced Sysmon as an optional built-in Windows feature from 2026; this room uses the standalone v15.15 deployment, which is valid on both OS builds listed.
  - Security 4688: NewProcessName; ParentProcessName ("Creator Process Name") added in Windows 10 and Server 2016; CommandLine ("Process Command Line", Windows 8.1 and Server 2012 R2 and later) is filled only when "Include command line in process creation events" is enabled; there is no original file name field. Sources: Microsoft 4688 documentation (https://technet.microsoft.com/es-es/itpro/windows/keep-secure/event-4675), EventSentry 4688 reference (https://system32.eventsentry.com/security/event/4688).
  - T1105 Ingress Tool Transfer lists certutil downloads; MITRE CAR-2021-05-006 "CertUtil Download With URLCache and Split Arguments" (https://attack.mitre.org/techniques/T1105/, https://car.mitre.org/analytics/CAR-2021-05-006). certutil -decode maps to T1140 and certutil -addstore Root to T1553.004 (MITRE ATT&CK technique pages).
  - certutil syntax used: -urlcache -split -f <URL> <outfile> (download), -urlcache * delete (clears URL cache entries), -verify -urlfetch <cert> (chain and revocation check with URL retrieval), -hashfile <file> SHA256, -decode <in> <out>, -addstore -f Root <cert>. certutil accepts both "-" and "/" option prefixes; "/urlcache /split /f" appears in public threat reports and detection rules. Sources: Microsoft certutil command reference (learn.microsoft.com/windows-server/administration/windows-commands/certutil), HYPR CRL cache guide for -urlcache * delete (https://docs.hypr.com/docs/auth/authInstallCfg/authInstallCfgPwc/authInstallCfgPwcAdvCfg/authInstallCfgPwcAdvCfgCerts/auth-install-cfg-pwc-adv-cfg-certs-delete-crl-cache-avoid-slow-logins/), Joe Security Sigma rule covering "/urlcache /f http" (detection.fyi).
